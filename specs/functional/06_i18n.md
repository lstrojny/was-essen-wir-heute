# Multi-language support

The app supports two languages: **German (`de`)** and **English (`en`)**. Each
user has a single **active language**, set in app settings, used to drive
both the UI and the display of user-authored content.

## App UI

UI strings (labels, buttons, errors, settings copy) exist in both supported
languages. Implementation details are a tech-spec concern.

## Content storage principle

User-authored text is stored **separately per language** in the supported set.
The active language picks which version is displayed. A missing translation
falls back to the other language, and the UI marks the fallback visually so
the user knows it is still untranslated.

The fields below are per-language; everything else on a recipe or ingredient
entry is language-independent.

## Recipes — per-language fields

Per-language text on a recipe:

- **Title**
- **Notes**
- **Steps** — the list of steps (its length and order) is **shared** across
  languages; only the text of each step is per-language. Adding, removing, or
  reordering steps affects all languages at once.

Language-independent recipe fields: active time, wait time, ingredients
(structured triple; *name* on a linked row resolves through the central
entry), components, ratings, source (kind, original ID/URL).

**Cuisine** is stored as a **language-independent key** drawn from a
controlled vocabulary (e.g. `italian`, `thai`, `german`). The app holds a
translation table that maps each key to a display label per supported
language. Filtering and search by cuisine work on the key, so they remain
language-agnostic.

## Central ingredients — canonical name per language

Each central ingredient entry has one **canonical name per supported
language**. The active language picks which canonical is displayed. If the
canonical for the active language is missing, the canonical for the other
language is shown and is visually marked as awaiting translation.

**Aliases** remain a single, language-agnostic list of strings used only for
matching during entry/import. The list may contain strings from any
language, which is what enables cross-language matching: typing `scallion`
in a German session still resolves to the entry whose German canonical is
`Frühlingszwiebel`.

Conversion data (role, density, per-unit mass) is language-independent.

## Imports

- **Spoonacular** arrives in English. The import enrichment step is extended
  to translate the title, notes, and each step into the other supported
  language so the saved recipe is bilingual. Cuisine is mapped to the
  controlled-vocab key (creating a new key if needed; see *Open questions*).
- **LLM chat** can take place in either language. The structured-emit step
  is prompted to produce title, notes, and step texts in **both** supported
  languages.
- When ingredient matching during import creates a new central entry, the
  enrichment LLM also proposes a canonical for the language not present in
  the source data.

## Manual creation and editing

A user creating a recipe manually fills text fields in their active
language; the other-language fields stay empty until populated.

Each per-language text field offers a **translate** action that
LLM-translates from the populated language to the empty one. The user
reviews the result before it is saved. The same action is available on
central ingredient entries.

## Fallback and search

- When an active-language text is missing, display the other-language text
  and mark it visually as untranslated.
- Search over recipes and ingredients matches against text in **both**
  supported languages and against aliases. A search for `onion` will find
  an entry whose only canonical is `Zwiebel`.

## Adding languages later

The two-language scope is a v1 simplification. The data model (per-language
fields keyed by language code, language-agnostic aliases) generalises to
more languages without a structural change. Expanding the set would require
UI work and a translation pass over existing content.

## Open questions

- **Per-recipe language override**. Whether the user can view a single
  recipe in a non-active language without changing the global setting.
  Useful when reading an English recipe while keeping the German UI.
- **Cuisine vocabulary growth**. When an import surfaces a cuisine not yet
  in the controlled list (e.g. a Spoonacular cuisine the app has never
  seen), whether the app auto-adds the key and prompts for translations,
  or surfaces it for explicit user confirmation first.
- **Alias normalisation for matching**. Case folding, diacritic stripping,
  etc. Belongs in tech spec.
