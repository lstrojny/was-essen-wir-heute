# Internationalisation

This file describes how the two-language scope from
`specs/functional/06_i18n.md` is implemented. The user-facing rules
(per-language fields, fallback marking, etc.) live in that functional
spec; this file covers the technical layer.

## Library

- **next-intl** for message catalogs, ICU MessageFormat plural handling,
  and number/date formatting. It integrates with App Router server and
  client components and resolves the active locale per request.
- Numbers and dates are formatted through next-intl's `getFormatter` /
  `useFormatter`, which wraps the platform's `Intl.NumberFormat` and
  `Intl.DateTimeFormat` with the active locale already bound.

## Routing

- **No URL-based locale prefix** (no `/de/...` vs `/en/...`). The locale
  is resolved server-side per request.

## Locale resolution

A single helper resolves the active locale for every request:

1. If the request is authenticated, use the logged-in user's `language`
   column (`de` or `en`).
2. Otherwise, parse the `Accept-Language` header and pick the
   highest-quality match against the supported set (`de`, `en`).
3. If nothing matches, fall back to **`de`** (the app's primary
   language; the project's name is German and the German-speaking family
   is the primary user).

No locale cookie. The user's stored `language` is the source of truth
once authenticated; public routes (`/login`, `/setup`) infer from the
browser per request.

Because the locale is resolved in the **root layout** (`getLocale()`
feeds `<NextIntlClientProvider locale messages>`), any server action
that mutates the authenticated user's `language` must invalidate that
layer so the next render picks up the new locale and message bundle.
Concretely, after writing the new `language` the action calls
`revalidatePath('/', 'layout')`; without that step the layout's cached
locale remains in effect until a hard reload.

## Message catalogs

- One JSON file per supported language at
  `src/i18n/messages/<locale>.json`.
- Top-level keys group by surface (`nav`, `login`, `setup`, `settings`,
  `admin.users`, `ingredients`, `errors`, …) to keep diffs readable as
  the app grows.
- Plurals use ICU `{count, plural, …}` form so German's `1 Alias` vs.
  `3 Aliasse` and English's singular/plural work consistently.

## Component conventions

- **Server components** read translations via
  `await getTranslations('namespace')`.
- **Client components** read translations via
  `useTranslations('namespace')` inside `NextIntlClientProvider`.
- The root layout sets `<html lang={locale}>` so screen readers and the
  browser get the right hint.

## Translatable-content forms

Editor surfaces for user-authored translatable text (recipe title and
notes, step text, ingredient canonical, ingredient alias groups,
cuisine label) render input fields for the **active locale only**.
There is no side-by-side per-locale editor. The active locale is the
one resolved per request (see *Locale resolution*); it drives both the
input rendered on the form and the label shown next to it. Other-locale
rows in `translated_strings` are read for display fallback (see
`specs/functional/06_i18n.md`) but are never rendered as editable
inputs alongside the active-locale input.

This keeps the UI surface independent of the number of supported
locales — adding a locale grows the data set but does not introduce
new columns of form fields.

## Number formatting

- Density (g/ml), grams-per-unit, and other free-form numeric display
  go through the formatter helper, not bare `String(n)` or `n.toFixed()`.
- Form **inputs** stay locale-tolerant on the client (accept both `.`
  and `,` decimal separators) and parse to a canonical IEEE-754 number
  in the server action. Storage is always canonical.

## Open questions

- **Adding a third language**: the data model supports it without a
  schema migration — user-authored translations live in
  `translated_strings` keyed by `(group_id, locale)` (see
  `01_persistence.md`). Bringing in a third locale requires extending
  the `locale` enum, growing the message catalog with a new file, and
  adding the locale to the resolver's supported set.
- **Time-zone-sensitive display** (e.g. timestamps shown to users): not
  needed in v1; revisit when meal plans land.
